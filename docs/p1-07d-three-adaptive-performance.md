# P1-07D — Three.js XR Adaptive Dynamic Texture Performance

Tracking issue: #38. Baseline: `main` @ `52ac8e5dc57c35b4ae179c0267807228936368f1`
(P1-07C merged; 429 unit/integration tests, 376 browser E2E tests, package
smoke passing).

As in P1-07C, this document separates three kinds of statement:

- **Observed:** measured values from `docs/evidence/p1-07d/`, generated by
  `scripts/bench-spatialflex.mjs` (summary, report, raw samples) and
  `apps/xr-lab/bench/visual.bench.ts` (rendered captures).
- **Inferred:** reasoning from those measurements and from the three.js,
  Babylon.js and browser behavior they point to.
- **Hypothesis:** not tested here.

P1-07C numbers are historical context only. Every before/after comparison
below was measured on the same machine, with the same configuration, in this
milestone; the unoptimized P1-07D code is the control.

## 1. Summary

- **Reproduced on current main** (unmodified `52ac8e5`, headless, 3 repeats):
  Three.js XR Adaptive at 20 panels and 10 Hz (W1) runs at a frame P95 of
  283 ms in Chromium, with 2.5 s of long tasks per 3 s window.
- **Root cause (confirmed by ablation):** every data update re-uploads each
  panel's 600 × 400 2D canvas into an **SRGB8_ALPHA8** texture, which is the
  format three.js allocates for `SRGBColorSpace`. Re-uploading a canvas into
  that format is slow in both browsers:
  - **Chromium** stalls on the GPU side. Main-thread JavaScript stays around
    1.4 ms/s, yet headed frames take 100 ms.
  - **Firefox** converts on the CPU inside `texSubImage2D`: 163 ms/s,
    against 11 ms/s for the same faces stored as RGBA8.
- **Ruled out** by instrumentation and ablation: canvas drawing, React
  reconciliation, redundant redraws or uploads, and mipmap generation on a
  hardware GPU.
- **Optimization (one change, Three.js host only):** the face canvas is
  stored as it is, in an RGBA8 texture. The face's own material decodes it
  from sRGB in the shader, which is the approach three.js uses for sRGB
  video textures. Unchanged: resolution, mipmaps, update rate, content,
  hover and selection feedback, Babylon.js and the SDK.
- **Result (same machine, 3 repeats, W1 at 20 panels):**
  - **Headed GPU Chromium:** frame median 91.6 → 8.3 ms (−91 %), P95
    125 → 8.5 ms (−93 %), P99 180 → 16.7 ms (−91 %).
  - **Headed Firefox:** upload-call CPU 140 → 9.5 ms/s (−93 %), render P95
    18.5 → 2.9 ms (−85 %), frame P95 33 → 25 ms.
  - **Headless Chromium** (software GL): P95 317 → 83 ms (−74 %).
  - **Headless Firefox:** unchanged.
- **First attempt failed, and was caught** (§6). React Three Fiber silently
  re-tags `map`-prop textures as sRGB. The fix therefore keeps the material
  inside `CanvasFace`, and a regression test now asserts the allocated
  format and the rendered colors.
- **Correctness:**
  - **Same-build checks:** after rapid updates, rendered panel pixels are
    identical (difference 0) to a fresh page that rendered only the final
    state, and clearly different from the previous state. Hover,
    selection, actions, manipulation and lifecycle are verified in
    Chromium and Firefox.
  - **Cross-build comparison:** the fix is **not pixel-identical** to the
    old rendering. 82 % of pixels are identical and 97 % are within 32
    levels. About 3 % differ more, at antialiased text edges: minified text
    is filtered in gamma space, as in Babylon.js, and looks slightly
    heavier (§7.3). This needs a reviewer decision.

## 2. Update pipeline audit

One W1 data tick follows this path (Three.js; Babylon.js shares the first
four steps):

```text
benchData tick (setInterval 100 ms)                  BenchmarkPage.tsx
  → useSyncExternalStore: every BenchItem re-renders  (React)
  → XR view re-declared: { title, body: {value}, actions }  (renderWidget)
  → useSpatialPresentations / PresentationRuntime snapshot   (@spatialflex/*)
  → XR Lab integration builds HostPanel[] (body = view.body)
  → ThreeHost <Scene> re-renders; Panel3D per panel (React Three Fiber)
  → Panel3D effect [title, body, selected] → CanvasFace.drawPanel()
  → drawPanelFace(): 2D canvas 600 × 400 (clear, border, text)
  → texture.needsUpdate = true
  → next WebGLRenderer.render(): texSubImage2D(canvas) into the
    SRGB8_ALPHA8 texture (texStorage2D, immutable) + generateMipmap
  → browser presents the WebGL canvas (GPU process / compositor)
```

Babylon.js: the host reconciles the same `HostPanel[]` imperatively, draws
with the same `drawPanelFace` into its `DynamicTexture` canvas, and calls
`texture.update()`. That call uploads at once with `texImage2D(canvas)` into
an **RGBA8** texture plus `generateMipmap`. The upload happens there, outside
`Scene.render()`.

**Measured per stage** (control, headless, 20 panels, W1; spans are
synchronous main-thread time):

| stage                              | Chromium                                           | Firefox                | how measured                           |
| ---------------------------------- | -------------------------------------------------- | ---------------------- | -------------------------------------- |
| React: `Panel3D` renders           | 20 per tick (one per changed panel)                | 20 per tick            | `three.panelRender` counter            |
| Face draws                         | 1 per changed panel; 0 unchanged                   | same                   | `three.faceDraw.*` counters            |
| Face draw CPU                      | 0.01–0.03 ms/call (recorded lazily)                | ~0.3 ms/call (58 ms/s) | `three.panelFaceDraw` span             |
| Texture dirty → uploads            | 1 : 1 (no coalescing needed: ≤ 1 update per frame) | 1 : 1                  | `three.textureDirty`, `gl.uploadCalls` |
| `texSubImage2D` call               | ~1 ms; 67–80 ms/s                                  | ~1 ms; 177–194 ms/s    | `gl.texSubImage2D` span                |
| `generateMipmap` call              | < 0.01 ms                                          | ~0.2 ms (34–42 ms/s)   | `gl.generateMipmap` span               |
| Texture allocations during updates | 0                                                  | 0                      | `gl.createTexture` counter             |
| Long tasks                         | 2.5 s per 3 s                                      | n/a (unsupported)      | Long Tasks API                         |

- **Chromium (inferred):** the GL calls return quickly while frames stall.
  The work happens in the GPU process, and the main thread waits for it when
  presenting.
- **Throughput collapse:** only ~10 of the 30 data ticks in a 3 s window run
  at all, because the main thread is blocked.
- **Firefox:** Three.js (upload 177 + draw 58 ms/s) and Babylon.js
  (`DynamicTexture.update` 242 ms/s) do the same total work. P1-07C's
  "render CPU 18 ms vs 2–3 ms" was mostly attribution: three.js uploads
  inside `render()`, Babylon.js outside it.

**Redundant work:** none observed.

- Every W1 tick changes every panel's value, so all 20 redraws are
  required.
- Re-declaring identical content (every item re-renders while only one value
  changes) produces exactly one draw and one upload; the change is tested
  in D2/D3.
- Panels are never re-created and textures are never re-allocated by data
  updates.

## 3. Instrumentation (benchmark mode only)

New optional instrumentation, installed only by `enableBenchmarkMode`
(`?fixture=benchmark` in test-hook builds) and fully uninstallable:

- **`apps/xr-lab/src/performance/textureInstrument.ts`:**
  - **WebGL wrappers** on `WebGL2RenderingContext.prototype` and
    `WebGLRenderingContext.prototype`, the same for both engines:
    `texImage2D`, `texSubImage2D`, `texStorage2D` and `generateMipmap`
    (spans). Counters: `gl.uploadCalls` and `gl.uploadPixels` for DOM and
    canvas sources, `gl.createTexture`, `gl.deleteTexture`.
  - **`CanvasFace.drawPanel` and `drawButton`:** spans, plus the draw reason
    (`initial`, `content`, `selection`, `unchanged`), `three.textureDirty`
    and `three.faceDispose`.
  - **Babylon `DynamicTexture.update`:** span.
- **Allocation format:** `gl.allocate.<format>` counts level-0
  `texStorage2D` and `texImage2D` allocations by internal format
  (`SRGB8_ALPHA8`, `RGBA8`, …). It was added after §6.
- **React counters** (no-ops without an active collector):
  `three.sceneRender`, `three.panelRender`, `three.panelCommit`.
- **Aggregation:** `summary.json` schema `/2` adds rates per second of
  window (draws, uploads, megapixels, CPU ms/s). Every `/1` field is
  unchanged, and P1-07C raw data still aggregates.

**Observed vs inferred:**

- **Observed:** call counts and the main-thread duration of each call.
- **Not GPU time:** a WebGL call's duration is not GPU execution time.
  Chromium queues the work to its GPU process; Firefox may convert and
  upload synchronously.
- **Uploads:** that `needsUpdate` leads to exactly one upload is checked
  with the `gl.uploadCalls` counter, not assumed.
- **GPU-side cost:** inferred from frame intervals and long tasks, which
  rise while main-thread JavaScript does not.

D8 tests (`textureInstrument.test.ts`) verify that the wrappers preserve
results, record nothing while not measuring, and restore the exact original
functions.

**Reading (observed):**

- **Uploading is the cost; drawing is not.**
  - A2 (draw, no upload) returns every environment to its idle cadence.
  - A1 (upload, no draw) does not help Chromium at all (headless P95
    300 → 300 ms).
- **The cost scales with pixels:** A3 cuts it.
- **On a hardware GPU it is the format, not mipmaps:**
  - In headed Chromium, A5 (RGBA8) brings the frame median from 100 ms to
    8.3 ms and P95 from 112 to 8.5 ms. A7 shows the re-allocation alone
    does nothing (§6). That equals Babylon.js on the same
    machine (8.3 / 8.5 ms).
  - A6 (no mipmaps) leaves it at 92 / 108 ms.
  - In headed Firefox, A5 cuts upload-call CPU from 163 to 11 ms/s and
    render P95 from 22 to 3.3 ms.

  - **RGBA8 (A5):** raises Chromium's completed uploads from 64/s to 175/s
    and lowers P95 from 300 to 100 ms. That is the same as Babylon.js
    headless (P95 100 ms).

    SwiftShader is CPU work.

**Not chosen as fixes:**

- **Halving the resolution (A3)** lowers text fidelity.
- **Dropping mipmaps (A6)** aliases a 600 px face shown at about 140 px on
  screen.
  Both remain diagnostics.

## 5. Optimization

**Change** (`apps/xr-lab/src/hosts/three/panelTexture.ts`, `Panel3D.tsx`):

```ts
// CanvasFace now owns its texture AND its material.
this.texture = new CanvasTexture(this.canvas);
this.texture.colorSpace = NoColorSpace;        // was SRGBColorSpace → RGBA8
this.material = new MeshBasicMaterial({ map: this.texture, toneMapped: false });
this.material.onBeforeCompile = decodeFaceColor; // sRGB decode in the shader

// decodeFaceColor: three.js's map_fragment chunk with an sRGB decode
"#ifdef USE_MAP
	diffuseColor *= sRGBTransferEOTF( texture2D( map, vMapUv ) );
#endif"

// Panel3D / PanelControl
<mesh material={face.material} ...>   // was <meshBasicMaterial map={face.texture} toneMapped={false} />
```

**Why this is equivalent:** the canvas holds sRGB-encoded pixels.

- **Before:** the GPU decoded them to linear on each texel fetch, through
  the SRGB8_ALPHA8 format.
- **Now:** the shader decodes the filtered sample, so rendered colors are
  the canvas's colors. They are measured in §7: the dominant face color is
  `#f6f8fa`.
- **Filtering:** bilinear filtering and mipmaps now operate on encoded
  values, as Babylon.js already does. Edges of antialiased text can
  therefore differ by a few levels; §7 gives the measured difference.
- **Precedent:** three.js uses this approach for sRGB video textures
  (`DECODE_VIDEO_TEXTURE` in `map_fragment`, "until browsers properly
  support SRGB8_ALPHA8").

**Why the face owns its material:** React Three Fiber re-tags any texture
applied through a material's JSX `map` prop as `SRGBColorSpace`. That is its
automatic sRGB conversion for built-in color maps. Setting the color space
on the texture alone is therefore silently undone (§6). Building the
material in `CanvasFace` keeps the storage format and its decode together.

**Scope:**

- **Files:** the Three.js host only: two source files and one unit test.
- **Unchanged:**
  - Babylon.js.
  - `@spatialflex/core`, `/dom` and `/react`, and every public API.
  - Texture resolution (`PIXELS_PER_METER` 1000), mipmaps and the 10 Hz
    data rate.
  - Panel content, hover, selection and control feedback.
  - Picking and `userData`.
  - `textureCreated()` and `textureDisposed()` probe semantics.
- **Disposal:** `CanvasFace.dispose()` now also disposes the material.
- **Shader programs:** one shared `onBeforeCompile` function, so every face
  material uses one program (unit-tested via `customProgramCacheKey`).

## 6. A failed first attempt, and how it was caught

**First attempt** (commit `3c8e0b9`): it set `colorSpace = NoColorSpace` on
the texture and passed it as `<meshBasicMaterial map={face.texture}
onBeforeCompile={decodeFaceColor} />`.

**How it failed:**

- The headless full matrix showed no Chromium improvement.
- Headed Chromium still ran at a 100 ms frame median (`attempt1-*` raw
  data).
- Its same-build pixel tests passed, because they compare a build with
  itself.

**Diagnosis** (headed Chromium, Three.js, 20 panels, W1, 3 repeats each;
`diag-*` raw data):

| run | change                                               | frame median (3 repeats) |
| --- | ---------------------------------------------------- | ------------------------ |
| E1  | attempt 1, W1 alone                                  | 100 / 100 / 25 ms        |
| E2  | attempt 1 without the shader decode (local)          | 92 / 100 / 100 ms        |
| E3  | attempt 1 + `face-linear` ablation                   | 8.3 / 8.3 / 8.3 ms       |
| E0  | original faces (local checkout)                      | 100 / 100 / 54 ms        |
| E4  | original faces + `face-realloc` (re-allocation only) | 100 / 100 / 100 ms       |
| G1  | attempt 1 + eager 2D context (local)                 | 100 / 100 / 100 ms       |
| G2  | attempt 1 + canvas drawn before first upload (local) | 100 / 100 / 88 ms        |

**What the logs showed:** logging the WebGL calls for one face showed
`texStorage2D(…, 35907 /* SRGB8_ALPHA8 */, 600, 400)` in the attempt-1
build. React Three Fiber's `map`-prop conversion had restored
`SRGBColorSpace`.

- **Why the ablation worked:** it sets the color space after the prop was
  applied, so it really did store RGBA8.
- **What attempt 1 actually did:** no speedup, and the shader decode was
  applied on top of hardware sRGB decoding, giving darker colors.

**How this is now guarded:**

- **Unit test:** the face owns its material and the decode.
- **Instrumentation:** counts allocations by internal format
  (`gl.allocate.*`).
- **E2E test (both browsers, both engines):** asserts no SRGB8_ALPHA8 face
  allocation, and the rendered background color `#f6f8fa` within ±3 levels.
  Run against the attempt-1 code it fails (30 SRGB8_ALPHA8 allocations for
  5 panels × 6 faces).
- **Cross-build pixel comparison (§7):** compares the fix with the control
  build.

## 7. Visual and functional correctness

### 7.1 Same-build rendered-pixel checks (`e2e/textures.spec.ts`)

Both engines are covered in Chromium and Firefox, and the tests run in the
normal E2E suite. Panel faces are compared as **rendered WebGL pixels**: page
screenshots, decoded in the browser. Equality is measured as the mean
absolute channel difference and the share of pixels differing by more than
16 or 48 levels.

| test                    | what it proves                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1/D6 rapid updates     | A 10 ms update timer (faster than frames) for 600 ms, then a burst of 7 synchronous updates in one task. Every panel's face then matches a **fresh page that rendered only the final state** with difference 0 in every run (all 5 panels, both engines, both browsers). It differs from the **previous state** in 1.3–4.5 % of pixels, so the check can fail. |
| D1 format and color     | Faces are allocated as RGBA8 (0 × SRGB8_ALPHA8), and the dominant rendered face color is `#f6f8fa` ± 3. Fails on the attempt-1 code.                                                                                                                                                                                                                           |
| D2/D3 redundant updates | One panel's value changes while every item re-renders: exactly 1 face draw, 1 dirty texture and 1 WebGL upload, and 0 texture allocations. Re-declaring identical content: 0 draws, 0 uploads.                                                                                                                                                                 |
| D4 interaction          | Hover feedback appears in the button's pixels and clears. The action runs exactly once per click. Selecting a panel draws its border; selecting another clears it (pixels back to the initial state).                                                                                                                                                          |
| D5 lifecycle            | 3 cycles of extract → update → move, rotate and scale with the real mouse → restore, then workspace unmount → remount with the same ids (new registrations) and changed data. Live textures return to their initial count each time, subscriptions are unchanged, and the re-shown panels match a fresh page at the same data.                                 |

Manipulation (move, rotate, scale) is also covered by the existing B4/B5,
manipulation and hardening specs, which are unchanged and pass. During W3
the instrumentation shows 0 texture allocations.

    filtered encoded values.

  Whether this rendering change is acceptable is a review decision (§12).
- **Not tested:** a fix that keeps linear-space filtering at RGBA8 upload
  speed would need a GPU copy or conversion pass into an sRGB texture. That
  is more than a narrow change.

## 11. Limitations and remaining costs

- **Software GL (headless Chromium) still saturates at 20 panels × 10 Hz,
  in both engines:**
  - **Three.js:** P95 83 ms after the fix; long tasks 1.9 s per 3 s.
  - **Babylon.js:** P95 83–100 ms.
  - **Cause:** the upload volume (48 Mpixel/s plus mipmaps) on a CPU
    rasterizer. It is not Three.js-specific.
  - **What the ablations suggest:** fewer pixels (A3) or no per-update
    mipmap (A6) would help. Both reduce fidelity, so neither was done.
  - **Status:** unresolved, documented.
- **Headless Firefox is unchanged:** its upload cost does not depend on the
  format in that configuration.
- **Headed Firefox frame P95 (25–33 ms) and P99 at 20 panels:** these are
  bimodal 8.3/16.7 ms cadence effects, also present for Babylon.js.
  Main-thread upload cost is no longer the limit.
- **Rendering change:** gamma-space filtering of text (§7.3) is a visible
  change, measured but not judged here.
- **GPU time is not measured directly:** GPU-side cost is inferred from
  frame intervals, long tasks and controlled ablations. No GPU timer
  queries or traces are used.
- **One machine, one low-end GPU (GT 710):** results on other GPUs,
  drivers, macOS and headsets are not measured. The direction is expected
  to hold, since three.js itself avoids SRGB8_ALPHA8 for frequently
  re-uploaded video; the magnitude is not.
- **Repeats:** 3 per scenario. Several headless and P99 values have CV
  > 20 % (marked `*`).

## 12. Recommendation and Multi-Surface implications

- **Recommendation: REVIEW REQUIRED.**
  - **Performance:** the confirmed root cause is fixed, with large measured
    gains on a real GPU and no regression in other workloads, Babylon.js,
    lifecycle or correctness.
  - **Decision for the reviewer:** whether the measured text-rendering
    change of §7.3 is acceptable. Minified text is filtered in gamma space,
    matching Babylon.js; 3 % of panel-region pixels differ by more than 32
    levels.
- **P1-08 Multi-Surface (estimates, not measured):**
  - **Per-surface upload cost:** each additional surface with dynamic
    canvas faces multiplies upload volume; the per-texture format choice
    stays important.
  - **Shared helper:** a shared "dynamic canvas texture" helper should own
    the format and decode, so this is not re-learned per surface.
  - **Metrics:** P1-08 should report upload Mpixel/s and allocations by
    format per surface. The instrumentation added here does that.
