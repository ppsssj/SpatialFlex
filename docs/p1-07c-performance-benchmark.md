# P1-07C — Performance & Scalability Benchmark

Tracking issue: #36. Baseline: `main` @ `5553871068a526861a1a6a1bd6c78ddf078cf4d0`
(420 unit/integration tests, 358 browser E2E tests, package smoke passing).

This document separates three kinds of statement:

- **Observed:** measured values. They come from `docs/evidence/p1-07c/`,
  generated by `scripts/bench-spatialflex.mjs`.
- **Interpretation:** engineering reasoning from those measurements and the
  source code.
- **Hypothesis:** not tested here.

The full generated tables are in `evidence/p1-07c/benchmark-report.md`. This
document quotes the rows its conclusions depend on.

## 1. Scope and methodology

The benchmark answers six questions:

1. How does cost scale with panel count?
2. How do Native DOM and XR Adaptive differ?
3. How do Three.js and Babylon.js differ?
4. Where is CPU time spent?
5. Do lifecycle cycles leak?
6. What should P1-08 (Multi-Surface) watch out for?

It measures the unoptimized implementation first. One narrow optimization
followed, justified by a diagnostic ablation, and it was measured before and
after under the same configuration (§13).

**Methodology summary** (the machine-readable form is
`evidence/p1-07c/methodology.json`):

- **Build:** production (`vite build`, `vite preview`) with test hooks, served
  cross-origin isolated (COOP/COEP) so `performance.now()` resolution is 5 µs
  in Chromium and 20 µs in Firefox. The development server is never used.
- **Isolation:** each repeat is a fresh page load, so there is no renderer,
  runtime or React tree carried between repeats. Workloads run sequentially
  with one browser at a time.
- **Measured windows:** 1 s warm-up, then a 3 s window bounded by explicit
  collector `start()`/`stop()` calls. W3 is a scripted drag sequence instead
  of a fixed window.
- **Repeats:** 3 for the main matrix, 2 for the ablation pairs.
- **Ordering:** scenario order is shuffled with a seeded PRNG (seed 7, recorded).
  W0, W1 and W2 run in a seeded order within each page. W3 always runs last
  because it changes poses (a documented ordering rule).
- **Validity:** each workload starts with a check for exactly N presentations
  of the requested kind, each visible inside the canvas and none overlapping
  another. Adaptive runs also check that the renderer draws exactly N panels.
  W3 additionally requires at least one observed manipulation commit. Invalid
  runs are excluded from aggregates and listed. This run had **0 invalid runs
  out of 488 scenario aggregates.**
- **Aggregation:** each run yields median, P95 and P99 over its samples. Each
  scenario reports the median of the per-run values across repeats, with min,
  max and coefficient of variation; `*` in the report marks CV > 20 %. Missing
  or unsupported values are `null` / `n/a`, never 0.

## 3. Test fixture and workloads

### Fixture

`apps/xr-lab/src/fixtures/BenchmarkPage.tsx` is enabled with
`?fixture=benchmark&panels=0|1|5|10|20`, in test-hook builds only. The
Dashboard and Hardening fixtures are unchanged.

- **Panels:** N real React components, ids `bench-1` to `bench-N`, each a
  registered `SpatialItem`. Each has:
  - local state and an interactive button;
  - a fixed 160×100 CSS-pixel layout;
  - a deterministic value, `(tick·(i+3) + 17i) mod 1000`;
  - an action counter;
  - a declared XR view (semantic `value` body and a `+1` action, never cloned
    HTML).
- **Presentation:** the harness (`performance/BenchmarkHarness.tsx`) starts
  presentations through the XR Lab's own `LabIntegration.extract` — the same
  call the Spatial Website UI makes — at grid positions:
  - 5 columns, 0.7 m × 0.62 m pitch, at z = −0.4 m;
  - Native DOM is scaled to the 0.6 m Adaptive width;
  - camera at (0, 1.42, 4), looking at (0, 1.42, −0.4), in both engines,
    through a `setCamera` test hook.
- **Validation:** every scenario's visibility and overlap were validated (§1).

## 5. Measurement instrumentation

All instrumentation lives in `apps/xr-lab/src/performance/`. It loads only for
`?fixture=benchmark` in test-hook builds; B3 checks that ordinary pages expose
none of it.

- **`collector.ts`:** a bounded collector, with every series a 20 000-sample
  ring buffer and no React state. It records:
  - rAF timestamps;
  - synchronous spans;
  - counters;
  - Long Tasks (`PerformanceObserver`, where supported);
  - interaction latency.
- **`instrument.ts`:** wraps SDK prototype methods without changing SDK code:
  - `NativeCompositor.composite` and `setTargets`;
  - `PresentationRuntime.extract`, `restore` and host `frame`;
  - `ItemManipulator.sync`;
  - `SpatialManipulator.update`.

  It also wraps the renderer submission:
  - Babylon: `Scene.render`;
  - Three.js: per-instance `render`, which three.js assigns in the
    `WebGLRenderer` constructor, captured with a prototype setter.

  `uninstall` restores the exact originals (B3). The cost of one timer pair is
  reported per run as `instrumentationCostMs`; it was below timer resolution
  (median 0) in every run.

- **`BenchmarkHarness.tsx`:** extraction, validity, state and handle points;
  the deterministic camera path.

**Interaction latency** is defined as follows:

- **`inputToCommit`:** `performance.now()` when the manipulation store
  notifies, minus the triggering pointer or key event's `timeStamp`.
- **`inputToNextFrame`:** `performance.now()` in the first animation-frame
  callback after that commit, minus the same `timeStamp`. This is the frame in
  which the renderer and compositor draw the new pose.

Neither includes display scan-out.

They hold every per-run sample, gzip-compressed (about 3.9 MB for all labels).

- `longTasks`, with `supported: false` where unsupported;

**Observed:**

- **Babylon `Scene.render` has a higher fixed CPU cost**: control 0.37–0.70

## 8. Native DOM performance

**Observed:**

- **JavaScript cost is linear and small.** `dom.composite` grows about 0.05 ms
  per panel at W2. At 20 panels it costs 1–2 ms per frame, about 6–13 % of a
  16.7 ms budget.
- **The frame cadence degraded much more than the JavaScript**: up to 185 ms
  per frame while all instrumented JavaScript in the frame stayed under 4 ms.
- **The cost is in browser rendering**, not in SDK code.

**Interpretation:** the ablation (§13) attributes this browser cost almost
entirely to the page surface's `clip-path`.

## 9. XR Adaptive performance

**Observed:**

- **The cadence holds** at 20 panels for W0, W2 and W3.
- **Renderer CPU grows roughly linearly**: about +0.03–0.07 ms per panel.
- **The SDK cost does not depend on the number of Adaptive panels**: no
  composite targets, and `core.itemSync` runs only when presentations change
  (about 0.005 ms).

The only Adaptive scaling problem is **content updates in the Three.js host**
(§7.3), measured as render P95 and long tasks.

**Interpretation:** the XR Lab's Three.js host repaints a 2D canvas and
re-uploads one texture per updated panel inside `render` (`hosts/three/`
panel texture path). Babylon's dynamic-texture path does not show the same
spikes. This is renderer-adapter code, not the SDK, and was not changed.

## 10. Three.js / Babylon.js comparison

See §7.3. Both engines run the same fixture and produce valid measurements
(B7). There is no SDK-level difference: the SDK cost is identical because the
runtime is renderer-neutral. The differences are in the hosts' own rendering
paths.

## 13. Optimization and before/after evidence

### Diagnostic ablation

The ablation (`--ablate page-clip`; same commit, paired control runs, 2
repeats) overrode only the page `clip-path` with `none`. It is a diagnostic
that changes the visuals, not a product measurement.

| Native 20, W2 (frame median / P95, ms) | Control       | Page clip removed |
| -------------------------------------- | ------------- | ----------------- |
| headless Chromium / Three              | 33.3 / 50.0   | 16.7 / 16.7       |
| headless Firefox / Three               | 185.1 / 226.6 | 16.6 / 28.8       |
| headless Firefox / Babylon             | 186.5 / 228.4 | 17.4 / 25.9       |
| headed Firefox / Three                 | 20.7 / 32.9   | 12.2 / 16.0       |
| headed Firefox / Babylon               | 25.7 / 33.9   | 8.6 / 9.1         |

### The change

- **Why:** the occlusion clip exists to cut out occluders in front of the
  page. `keep` (the native footprints) only exempts native descendants from a
  clip that cuts holes. With no hole, `outer ∪ keep` clips nothing that
  matters. `occlusionClipPath` already returns `none` in that case without
  natives, and `surface.spec.ts` asserts `none` once no occluder is in front of the page.
- **What:** the XR Lab page surface (`useSurfaceCompositor`, the page clip's
  owner since P1-07B3) now writes `none` unless an occluder cuts a hole. With
  holes it still calls the SDK's `pageClipPath`, which is unchanged together
  with its existing unit test.
- **Regression tests** (`runtimeMigration.test.tsx`):
  - Native presentations without occluders leave the page clip `none`.
  - An Adaptive panel in front of the page yields the outer loop, its hole
    and the native footprint.
  - Removing the panel returns the clip to `none`.
- **Existing E2E** for surface, native, hardening, manipulation and migration:
  90/90 passed before re-measuring.

| headed Chromium / Three W2 P95                    | 18.9          | **10.2**        |
| headed Firefox / Three W2 frame median / P95      | 25.6 / 34.0   | **15.9 / 22.1** |
| headed Firefox / Babylon W2 frame median / P95    | 41.7 / 41.7   | **8.6 / 9.1**   |

The Native path now scales like the Adaptive path and the 0-panel control at
20 panels.

**Regression observed:** in headed Chromium, `dom.composite` JavaScript time
rose from 0.38 to 0.74 ms (5 panels) and from 0.99 to 1.34 ms (20 panels).
Headless Chromium and Firefox show no such rise.

**Hypothesis (not tested):** with the page no longer clipped, the forced
style recalculation inside `composite` covers more of the page's subtree. The
net effect on frame cadence is strongly positive.

**Unchanged by this fix:**

- Scenes where Adaptive panels occlude the page while natives are present
  still pay the path clip. They were not benchmarked (§14, §15).
- Bottleneck 2 (Three.js texture updates).

## 14. Limitations and confidence

- **One machine.** It has a low-end discrete GPU (GT 710) and a 6-core
  desktop CPU. Headless Chromium uses software WebGL (SwiftShader). Results
  are relative evidence, not consumer, laptop or headset numbers.
- **Not measured:** GPU time, total browser memory and GPU memory.
- **Firefox:** heap and Long Tasks are unavailable. Its rAF cadence alternates
  between about 8.3 and about 15.8 ms between runs, so Firefox
  frame-median differences under about 2× are within noise (see the CV
  markers).
- **Mixed scenes untested:** Native plus occluding Adaptive panels are not
  part of the matrix. The optimization does not cover that case.
- **Residual heap growth unexplained:** about 10 KB per cycle at cycle 40. A
  heap-snapshot comparison (`HeapProfiler.takeHeapSnapshot`) over more cycles
  is the next step.
- **Fixed W3 drag workload:** pointer steps are paced one per animation frame
  and target only panel 1.
- **Ablation labels change visuals** by design; they are diagnostics, not
  results.
- **Confidence:**
  - High for the Native page-clip finding: a large effect, reproduced in both
    browsers, both engines and both modes, ablated and fixed.
  - Medium for engine CPU comparisons (small absolute values).
  - Low for absolute frame rates.

## 15. Multi-Surface implications (estimates, not measured)

Only a single source surface was tested. These are extrapolations.

- **Per-surface composition:** `dom.composite` is linear in native targets.
  S surfaces with N natives each would cost about S·N·0.05 ms per frame at W2
  (measured per-panel slope). That is about 5 ms for 100 natives.
- **Page clips (estimate, highest risk):** each surface would carry its own
  clip. Any occluder in front of a surface reinstates the `path()` clip
  measured above at 58–185 ms (headless Firefox) or 21–42 ms (headed Firefox)
  per frame for 5–20 natives. Cross-surface occlusion would make overlapping
  surfaces occlude each other: the very case that keeps the clip. This is the
  highest-risk cost for P1-08.
- **Occlusion math:** `localHoles` is surfaces × occluders per surface frame
  (quadratic in the number of overlapping surfaces). It is cheap at the
  sizes measured; unmeasured at multi-surface scale.
- **Camera ownership:** the runtime has one authoritative frame source.
  Multiple surfaces rendered by different hosts need per-host frames and
  per-surface target grouping. Today a second host's frames are ignored by
  design (P1-07B3).
- **Input routing:** handle rays come from the authoritative frame.
  Per-surface hit testing will add per-event work proportional to the number
  of surfaces. Not measured.
- **Registrations and presentations:** extract, switch and restore of 20
  presentations take under 10 ms of JavaScript. Hundreds would still be
  tens of ms per bulk operation (estimate).
- **Bridge (iframe) overhead:** not measured in this benchmark.

**Metrics to add with Multi-Surface:**

- per-surface `composite` and page-clip spans;
- clip-path loop counts per surface;
- occluder × surface pair counts;
- per-host frame cadence;
- cross-surface input latency;
- bridge message rate and latency.

## 16. Recommended P1-08 architectural priorities

1. **Avoid `clip-path` on a page that has native descendants**, and treat it
   as the critical path for occlusion design. Candidates (untested):
   - composite natives outside the page subtree (their own layer) so page
     clips never clip them;
   - clip only the page's own content box;
   - restrict holes to occluders that actually overlap natives or the page.

   Measure each with this benchmark's ablation method.

2. **Route frames per surface and host:** a per-surface `ContainingSurface`
   and authoritative frame, rather than one runtime frame source.
3. **Keep the SDK cost linear and small:** batch layout reads before style
   writes in `composite` if per-surface counts grow (bottleneck 3), and
   re-measure.
4. **Renderer adapters should throttle or batch content texture updates**
   (bottleneck 2) before multi-surface scenes multiply them.
5. **Extend this benchmark with:**
   - a mixed Native + occluding-Adaptive scene;
   - S = 1, 2, 4 surfaces;
   - heap-snapshot diffs for W4.
