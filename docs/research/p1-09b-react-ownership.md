# P1-09B: React ownership and state-preserving relocation

## Research scope

P1-09A established that direct reparenting outside a React root loses CSS context and delegated events. This spike tests whether different ownership and browser-move mechanisms change that outcome. The fixture is a React 19 component with local state, controlled input, context, a parent click handler, CSS ancestry, container query, animation and a custom element. It deliberately moves the existing React-managed node; this is characterization, not a supported ownership transfer or an SDK implementation.

Reproduce with `pnpm --filter @spatialflex/xr-lab exec playwright test -c playwright.react-ownership.config.ts`. Tests use a separate Vite page and port 4188; the existing P1-09A page remains untouched. Test environment: Windows, Node 24.12.0, Playwright 1.65.1, headless Chromium 159.0.8154.6 and Firefox 159.0. Browser version numbers are from the local Playwright installations, not support claims for all users.

These categories are scoped to the specific fixtures. A DOM input's retained text, React state before the move, and continued React updates are distinct: append/moveBefore retain the same DOM node and previous state, but events no longer update React when the node is outside its event root. Same-root events working is an observation, not React support for imperative reparenting. A direct move into a second React root also left the counter unchanged on click in both browsers.

Stable `createPortal` from initial render preserved context, state, events and synthetic parent bubbling on rerender. Switching a portal container caused cleanup and new mount, replaced the node, reset count and controlled input and lost focus. Changing a normally rendered mounted child into a portal also remounted in this fixture. Do not infer that portal can transparently relocate an arbitrary already-mounted component without application cooperation. React's documented portal contract describes logical parent context and bubbling; see [React createPortal](https://react.dev/reference/react-dom/createPortal).

`appendChild` and `insertBefore` preserved selection values in this fixture but lost focus, replaced the CSS animation instance, and caused the custom element to disconnect and reconnect. Feature-detected `moveBefore()` was available in both tested browser versions; it kept focus and selection, retained the same animation instance and produced `connectedMoveCallback` rather than disconnect/reconnect. Moving with `moveBefore` outside the React root still lost React delegated event behavior. Attempts to move a connected node into a disconnected target or a different document threw `HierarchyRequestError` in both browsers. This compares implementations of the API, not a polyfill; support must be feature detected. See [MDN Element.moveBefore](https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore).

Twenty append/restore cycles within the root followed by one click gave one state update and normal cleanup. A direct root unmount while the card was inside another part of the same root removed the containing DOM; after moving outside the root, unmount ran effect cleanup but left an orphan. Removing the moved child via React while it was in the same-root destination produced a `removeChild` error and React warning in both browsers. StrictMode development rendering recorded two effect mounts and one cleanup before final unmount. Replacing the original parent after a same-root move left two card DOM nodes while the old React effect cleaned up, without a page error in both browsers. Direct moveBefore unmount outside the root also leaves an orphan; other moveBefore removal arrangements, focus restoration after every strategy, independent listener-count instrumentation, and performance were not tested; no performance claims are made.

## Existing SpatialFlex and architectural options

`SpatialItem` retains children in the same DOM/React ancestry, adjusting positioning and reserving or collapsing the source footprint. `NativeCompositor` applies presentation styles to the original node and does not reparent it; it checks containment and hides unsupported compositions. This existing approach preserves identity and avoids treating a physical DOM move as React ownership, but remains constrained by containing blocks, ancestor clipping and compositor requirements. The Adaptive path provides a separate declared spatial view and actions, rather than promising arbitrary original DOM fidelity.

- **Transparent extraction:** direct reparenting needs no app rewrite but fails event ownership and CSS context outside the root, and unsafe React removal is demonstrably hazardous. `moveBefore` improves browser state but does not repair ownership.
- **Cooperative portal:** an application-controlled stable portal can preserve React context and events. The application must supply/own a stable portal host from initial render or hoist state; switching an already-mounted child or portal target can remount. CSS ancestry still changes.
- **Hybrid:** the existing Native/Adaptive split is a plausible starting point when users can choose tradeoffs, but this spike does not prove a complete XR integration or remove accessibility, containment and semantic-action limitations.

No option is established as universally correct. P1-09C should investigate a stable cooperative portal host moved without retargeting, lifecycle-safe ownership/cleanup, focus behavior, CSS context strategy and a separate accessibility/hit-testing matrix; compare with the existing same-ancestry Native path before proposing a new runtime. No novel CSS engine or full support claim follows from these experiments.

In this fixture the original and same-root card border-box measured 274 by about 221.8 CSS px in both engines. Outside-root relocation and initial portal placement measured 250 by about 125.9 px. This is one layout and includes the loss of ancestor padding and query-derived styling; it is not an intrinsic portal-size rule.
